## 1. Theoretical Questions

### 1. What is a JOIN in SQL? Why are JOINs necessary in relational databases? Explain the role of primary keys and foreign keys.

**Answer:**

A `JOIN` is a SQL operation used to combine rows from two or more tables based on a specified relationship or matching condition.

In relational databases, information is commonly divided into multiple tables to reduce redundancy, improve data consistency, and represent relationships between entities.

For example, an organization may store employee information in an `employees` table and department information in a separate `departments` table.

Instead of repeating department names and locations for every employee, the employee table can store a `department_id` referencing the department table.

**Example:**

**Table: employees**

| emp_id | name | department_id |
|---|---|---|
| 101 | Amit | 1 |
| 102 | Priya | 2 |
| 103 | Rahul | 1 |

**Table: departments**

| department_id | department_name |
|---|---|
| 1 | IT |
| 2 | HR |

To retrieve employee names with their department names:

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name
FROM employees AS e
INNER JOIN departments AS d
    ON e.department_id = d.department_id;
```

**Primary Key:**

A primary key uniquely identifies each row in a table.

For example, `departments.department_id` may be defined as a primary key.

**Foreign Key:**

A foreign key is a column or group of columns constrained to reference a primary or unique key in another table.

For example, `employees.department_id` may reference `departments.department_id`.

**Important Points:**

- JOINs retrieve related information stored across multiple tables.
- A primary key uniquely identifies rows and cannot contain NULL values.
- A foreign key enforces referential integrity when a foreign key constraint is defined.
- A foreign key column can contain duplicate values.
- A foreign key may allow NULL unless a `NOT NULL` constraint is specified.
- JOINs can be performed even without declared foreign key constraints.
- Table aliases such as `e` and `d` improve query readability.
- The `ON` clause specifies the matching condition between tables.

### 2. What is an INNER JOIN? How does it work, and what happens when no matching record exists?

**Answer:**

An `INNER JOIN` returns combinations of rows from two tables when the specified join condition evaluates to `TRUE`.

Rows without matching records are excluded.

**Syntax:**

```sql
SELECT
    column_list
FROM table_a
INNER JOIN table_b
    ON table_a.common_column = table_b.common_column;
```

**Example:**

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name
FROM employees AS e
INNER JOIN departments AS d
    ON e.department_id = d.department_id;
```

**Explanation:**

1. PostgreSQL examines the join condition.
2. Matching employee and department rows are combined.
3. Employees without a matching department are excluded.
4. Departments without matching employees are excluded.

**Important Points:**

- `INNER JOIN` returns only matching row combinations.
- The `INNER` keyword is optional; `JOIN` means `INNER JOIN` by default.
- A matching key appearing multiple times can produce multiple output rows.
- `NULL = NULL` does not evaluate to `TRUE`, so ordinary equality does not match NULL join keys.
- JOIN conditions should normally use columns that represent a meaningful relationship.
- INNER JOIN is commonly used to retrieve employees, orders, customers, and other related records.

### 3. What are LEFT JOIN and RIGHT JOIN? How do they differ from INNER JOIN?

**Answer:**

`LEFT JOIN` and `RIGHT JOIN` are outer joins that preserve rows from one side of the join even when matching rows do not exist on the other side.

**LEFT JOIN:**

A `LEFT JOIN` returns all rows from the left table and matching rows from the right table.

When no matching right-side row exists, the right-side columns are returned as `NULL`.

**Example:**

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.department_id;
```

This query retains all employees, including those without an assigned department.

**RIGHT JOIN:**

A `RIGHT JOIN` returns all rows from the right table and matching rows from the left table.

When no matching left-side row exists, the left-side columns are returned as `NULL`.

**Example:**

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name
FROM employees AS e
RIGHT JOIN departments AS d
    ON e.department_id = d.department_id;
```

This query retains all departments, including those without assigned employees.

**Comparison:**

| JOIN Type | Rows Preserved |
|---|---|
| INNER JOIN | Only matching row combinations |
| LEFT JOIN | All left-table rows |
| RIGHT JOIN | All right-table rows |

**Important Points:**

- `LEFT JOIN` is also called `LEFT OUTER JOIN`.
- `RIGHT JOIN` is also called `RIGHT OUTER JOIN`.
- `OUTER` is optional in PostgreSQL.
- A LEFT JOIN can be rewritten as a RIGHT JOIN by reversing table positions.
- Missing matches produce NULL values in columns from the unmatched side.
- Filtering right-table columns in `WHERE` may accidentally remove unmatched rows from a LEFT JOIN.
- Place conditions carefully in `ON` or `WHERE` depending on the intended result.

### 4. What are FULL OUTER JOIN and CROSS JOIN? Explain their differences and practical use cases.

**Answer:**

`FULL OUTER JOIN` and `CROSS JOIN` combine tables in fundamentally different ways.

**FULL OUTER JOIN:**

A `FULL OUTER JOIN` returns all matching row combinations, along with unmatched rows from both tables.

For unmatched rows, columns belonging to the missing side contain `NULL`.

**Syntax:**

```sql
SELECT
    column_list
FROM table_a
FULL OUTER JOIN table_b
    ON table_a.common_column = table_b.common_column;
```

**Example:**

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name
FROM employees AS e
FULL OUTER JOIN departments AS d
    ON e.department_id = d.department_id;
```

This includes employees without departments and departments without employees.

**CROSS JOIN:**

A `CROSS JOIN` produces the Cartesian product of two tables.

Every row from the first table is paired with every row from the second table.

**Example:**

```sql
SELECT
    d.department_name,
    p.project_name
FROM departments AS d
CROSS JOIN projects AS p;
```

If the departments table contains 4 rows and the projects table contains 6 rows, the result contains:

`4 × 6 = 24 rows`

**Comparison:**

| Feature | FULL OUTER JOIN | CROSS JOIN |
|---|---|---|
| Matching condition | Usually uses ON | No matching condition |
| Unmatched rows | Preserved from both sides | Every possible pair is generated |
| Typical use | Find missing relationships | Generate combinations |
| Result size | Depends on matches and duplicates | Product of input row counts |

**Important Points:**

- `FULL JOIN` and `FULL OUTER JOIN` are equivalent.
- FULL OUTER JOIN is useful for comparing two datasets.
- CROSS JOIN produces all possible row combinations.
- CROSS JOIN does not require an `ON` clause.
- Large CROSS JOIN operations can generate very large result sets.
- Use CROSS JOIN only when all combinations are actually required.

### 5. How can multiple tables be joined in a single SQL query? Explain table aliases, JOIN conditions, and the difference between ON and WHERE.

**Answer:**

SQL supports joining more than two tables in a single query.

Multiple joins are useful when retrieving related information distributed across several entities.

For example:

- `employees` stores employee details.
- `departments` stores department details.
- `projects` stores project information and assigned employee IDs.

**Example:**

```sql
SELECT
    e.emp_id,
    e.name,
    d.department_name,
    p.project_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.department_id
LEFT JOIN projects AS p
    ON e.emp_id = p.emp_id;
```

**Explanation:**

1. Start with the employees table.
2. Match employees to departments using `department_id`.
3. Match employees to projects using `emp_id`.
4. Preserve employees without departments or projects because LEFT JOIN is used.
5. Return the requested columns from all three tables.

**Table Aliases:**

Aliases provide shorter names for tables.

```sql
employees AS e
departments AS d
projects AS p
```

This helps avoid ambiguity when multiple tables contain similarly named columns.

**ON vs WHERE:**

The `ON` clause specifies the matching condition for a JOIN.

The `WHERE` clause filters rows after the joined result is formed.

**Example:**

```sql
SELECT
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.department_id
WHERE e.salary >= 60000;
```

This retains employees earning at least 60,000, including employees without departments.

However:

```sql
SELECT
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.department_id
WHERE d.department_name = 'IT';
```

This removes employees whose department is NULL or not IT.

**Important Points:**

- Multiple JOIN clauses can combine three or more related tables.
- Table aliases make complex queries easier to read.
- Qualify ambiguous columns with table aliases.
- `ON` defines join matching conditions.
- `WHERE` filters the resulting rows.
- A one-to-many relationship can produce multiple rows for one employee.
- `COUNT(*)` after a one-to-many JOIN counts joined rows, not necessarily unique employees.
- `COUNT(DISTINCT e.emp_id)` can count unique employees when needed.

## 2. Practical SQL Query Challenges

**Dataset:** `employee_day5.csv`, `departments_day5.csv`, `projects_day5.csv`

**Tables:** `employee_day5`, `departments_day5`, `projects_day5`

### Table 1: employee_day5

| Column | PostgreSQL Data Type | Description |
|---|---|---|
| emp_id | INTEGER PRIMARY KEY | Unique employee identifier |
| name | VARCHAR(100) | Employee name |
| department_id | INTEGER | Nullable reference to departments |
| salary | INTEGER | Monthly salary |
| city | VARCHAR(50) | Work location |
| experience_years | INTEGER | Years of experience |

### Table 2: departments_day5

| Column | PostgreSQL Data Type | Description |
|---|---|---|
| department_id | INTEGER PRIMARY KEY | Unique department identifier |
| department_name | VARCHAR(50) | Department name |
| location | VARCHAR(50) | Department office location |

### Table 3: projects_day5

| Column | PostgreSQL Data Type | Description |
|---|---|---|
| project_id | INTEGER PRIMARY KEY | Unique project identifier |
| project_name | VARCHAR(100) | Project name |
| emp_id | INTEGER | Nullable reference to an employee |
| budget | INTEGER | Project budget |
| status | VARCHAR(30) | Project status |

### Dataset Requirements

The Day 05 dataset should contain:

- 30 employees.
- 6 departments.
- 15 projects.
- Some employees with `NULL` department IDs.
- At least one department without employees.
- Some employees without assigned projects.
- At least one employee assigned to multiple projects.
- Some projects with `NULL` employee IDs.

These cases are intentionally included to demonstrate different JOIN behaviors.

### Query Challenges

**1. Retrieve employees with their department details using INNER JOIN.**

Retrieve:

- `emp_id`
- `name`
- `department_name`
- `location`
- `salary`

Include only employees with matching department records.

Sort by `department_name ASC`, followed by `salary DESC`, and then `emp_id ASC`.

**Concepts:** `INNER JOIN`, `ON`, table aliases, multi-column sorting.

**2. Identify employees without assigned departments using LEFT JOIN.**

Retrieve:

- `emp_id`
- `name`
- `salary`
- `department_id`

Include only employees whose department is missing.

Use a `LEFT JOIN` and identify unmatched department records rather than filtering the employee table directly for NULL values.

Sort by `emp_id ASC`.

**Concepts:** `LEFT JOIN`, unmatched rows, `IS NULL`, foreign key relationships.

**3. Identify departments without employees using RIGHT JOIN.**

Retrieve:

- `department_id`
- `department_name`
- `location`

Use a `RIGHT JOIN` between employees and departments.

Include only departments having no matching employee records.

Sort by `department_id ASC`.

**Concepts:** `RIGHT JOIN`, unmatched records, `IS NULL`.

**4. Retrieve employee and project information using FULL OUTER JOIN.**

Retrieve:

- `emp_id`
- `name`
- `project_id`
- `project_name`
- `status`

Include:

- Employees with assigned projects.
- Employees without assigned projects.
- Projects without assigned employees.

Sort by `emp_id ASC NULLS LAST`, followed by `project_id ASC NULLS LAST`.

**Concepts:** `FULL OUTER JOIN`, unmatched rows, `NULL`, `NULLS LAST`.

**5. Generate department-wise project assignment statistics using multiple JOINs.**

For every department, retrieve:

- `department_id`
- `department_name`
- `total_employees` — number of distinct employees belonging to the department.
- `assigned_employees` — number of distinct employees with at least one assigned project.
- `total_projects` — number of projects assigned to employees in the department.
- `total_project_budget` — sum of project budgets assigned to employees in the department; display zero if no projects exist.

Include departments with no employees and departments whose employees have no projects.

Sort by `total_projects DESC`, followed by `department_name ASC`.

**Concepts:** Multiple `LEFT JOIN` operations, `COUNT(DISTINCT)`, `COUNT()`, `SUM()`, `COALESCE()`, `GROUP BY`, one-to-many relationships.
